# JWT 해석과 활성 세션 검증을 분리하기

개인 프로젝트 · 변경 기록 2026.11.16 · 회고 작성 2026.11.16

토큰을 해석할 수 있다는 사실만으로 현재 로그인 세션이 유효하다고 판단하지 않도록, JWT의 식별자와 Redis에 등록된 활성 세션을 함께 확인하는 경계를 추가했습니다.

## 코드에서 확인한 흐름

`JwtSessionValidator`는 토큰 해석을 `JwtTokenDecoder`에 맡긴 뒤 아래 순서로 판정합니다.

1. 토큰 데이터가 존재하고, 생성 상태와 만료 조건을 만족하는지 확인합니다.
2. 세션 ID로 Redis 저장 데이터를 조회합니다.
3. 저장된 세션도 활성 상태인지 확인합니다.
4. 토큰과 저장 데이터의 세션 ID·회원 식별자가 일치할 때만 저장된 세션을 반환합니다.
5. 조회 결과가 없거나 검증 과정에서 예외가 발생하면 인증 가능한 결과를 반환하지 않습니다.

검증 메서드는 조회만 수행합니다. 세션 생성·저장은 이 경계의 책임으로 넣지 않았습니다. 검증에 실패한 요청이 새 세션을 만들면서 허용되는 흐름을 피하기 위한 구분입니다.

## 테스트가 확인하도록 작성된 조건

| 입력·상태 | 기대 결과 |
|---|---|
| 토큰과 Redis의 활성 세션 일치 | 저장된 세션 반환 |
| 삭제되었거나 등록되지 않은 세션 | 거절 |
| 회원 식별자 불일치 | 거절, 저장 데이터 덮어쓰기 없음 |
| 토큰 만료 | 거절, Redis 조회 생략 |
| 저장된 세션 만료 | 거절 |
| 토큰 해석 오류 또는 Redis 장애 | 거절 |
| 모든 검증 시나리오 | 세션 저장 호출 없음 |

테스트는 토큰 해석기와 저장소를 Mockito로 대체합니다. 따라서 이 단위 테스트의 범위는 검증 분기와 저장 부작용이며, 실제 JWT 암호 검증·Redis 네트워크·전체 로그인 흐름까지 증명하지 않습니다.

## 선택에 따른 비용과 다음 검증

Redis를 확인하지 못하면 요청을 허용하지 않는 방향입니다. 인증 상태를 확인할 수 없을 때 접근을 막는 대신 Redis 장애가 인증 가용성에 영향을 줄 수 있습니다. 운영 적용에는 예외 분류·관측과 장애 대응, 실제 저장소를 포함한 통합 검증이 별도로 필요합니다.

이 글은 기존 변경 코드와 테스트 소스를 대조한 기록입니다. 이번 문서 작성 과정에서 테스트를 다시 실행하거나 부하 성능을 측정하지 않았습니다. 전체 보안 검증 완료나 운영 배포 완료를 뜻하지 않습니다.

**근거:** 개인 프로젝트 커밋 `feda12cd`, `JwtSessionValidator`와 `JwtSessionValidatorTest`. 원본 저장소의 비공개 접근 정보·운영 설정은 포함하지 않았습니다.
